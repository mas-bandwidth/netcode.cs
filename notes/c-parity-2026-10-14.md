## 1. Wire format: packet types, prefix byte, sequence, nonce, AEAD AD, sizes, address values

**Verdict: MATCH**

The C# port implements the wire format described in `STANDARD.md` § Packets
and § Connect Token / Challenge Token.

- The seven packet type constants are declared exactly as the standard names
  them: `src/Netcode.cs:878-888` (`PacketType`).
- The address-family wire values are `IPv4 = 1` and `IPv6 = 2`:
  `src/Netcode.cs:173-181` (`AddressType`).
- The prefix byte is assembled as `(num_sequence_bytes << 4) | packet_type`
  on write: `src/Netcode.cs:950`.  On read the low nibble is the packet type
  and the high nibble is the sequence-byte count: `src/Netcode.cs:1098-1118`.
- Sequence numbers omit high zero bytes and are written/read little-endian with
  `1..8` bytes: `src/Netcode.cs:905-916`, `src/Netcode.cs:1126-1128`.
- The 12-byte IETF nonce for encrypted packets is four zero bytes followed by
  the 64-bit little-endian sequence: `src/Netcode.cs:974-979` (write) and
  `src/Netcode.cs:1151-1156` (read).  Challenge-token nonce construction uses
  the same pattern: `src/Netcode.cs:647-652`.
- AEAD associated data for encrypted packets is `[version info][protocol id][prefix byte]`:
  `src/Netcode.cs:966-972` and `src/Netcode.cs:1143-1149`.
  The private connect-token AD is `[version info][protocol id][expire timestamp]`:
  `src/Netcode.cs:594-600`.  Challenge-token AD is empty: `src/Netcode.cs:659`.
- Connection-request packet size is exactly `1 + 13 + 8 + 8 + 24 + 1024 = 1078`
  bytes: `src/Netcode.cs:902-903`.  Decrypted challenge/response payload size is
  checked to be exactly `8 + 300 = 308` bytes: `src/Netcode.cs:1193-1200`.
- IPv4/IPv6 addresses serialize/deserialize with the expected wire layout:
  `src/Netcode.cs:547-592`.

No divergence found in the port's wire format against `STANDARD.md`.

## 2. Replay protection: window 256, overflow-safe compare, decrypt/advance ordering, sentinel

**Verdict: MATCH**

- Replay window size is 256: `src/Netcode.cs:67` (`Defines.ReplayProtectionBufferSize`)
  and `src/Netcode.cs:1243` (`ulong[256]`).
- The overflow-safe distance check uses subtraction on the most-recent side:
  `src/Netcode.cs:1261-1263` (`MostRecentSequence >= 256 && sequence <= MostRecentSequence - 256`).
- The replay test happens *before* decryption: `src/Netcode.cs:1132-1139`.  The
  replay window is advanced *after* successful decryption:
  `src/Netcode.cs:1177-1178`.
- The "not yet received" sentinel is `UInt64.MaxValue`, filled on reset:
  `src/Netcode.cs:1250-1253`.
- Replay protection is applied only to keep-alive, payload and disconnect
  packets (the packet-type gate checks `packetType >= ConnectionKeepAlive`):
  `src/Netcode.cs:1132`; `ConnectionRequest`, `ConnectionDenied`,
  `ConnectionChallenge` and `ConnectionResponse` are not protected, matching
  `STANDARD.md` § Replay Protection.

## 3. Connect token: sizes, version info, create/expire, address count, user data, timeout, AEAD, history, encryption-manager count, expiry

**Verdict: mostly MATCH; one DIVERGENCE on `Stop()` state and one finding needing C lines**

- Public token size 2048, private token size 1024, challenge token size 300:
  `src/Netcode.cs:38`, `src/Netcode.cs:60`, `src/Netcode.cs:61`.
- Version info "NETCODE 1.02" with NUL terminator:
  `src/Netcode.cs:54`, `src/Netcode.cs:76`.
- `create_timestamp <= expire_timestamp` is enforced on read:
  `src/Netcode.cs:727-728` and in generation: `src/Netcode.cs:825-826`.
- Up to 32 server addresses: `src/Netcode.cs:46`, validated on read at
  `src/Netcode.cs:736-740`.
- User data 256 bytes: `src/Netcode.cs:44`; written/read as a fixed 256-byte
  block: `src/Netcode.cs:518`, `src/Netcode.cs:543`.
- Timeout seconds is a uint32 field: `src/Netcode.cs:512`, `src/Netcode.cs:529`,
  `src/Netcode.cs:733`, `src/Netcode.cs:827`.
- Private-token AEAD is XChaCha20-Poly1305 with a 24-byte nonce:
  `src/Netcode.cs:603-609`, `src/Netcode.cs:823`, `src/Netcode.cs:822-823`.
- Private-token AD is `[version info][protocol id][expire timestamp]`:
  `src/Netcode.cs:594-600`.
- Connect-token history size is `8 * MaxClients` (2048 entries):
  `src/Server.cs:28`.
- Encryption-mapping count is `4 * MaxClients` (1024):
  `src/Netcode.cs:1507`.
- Encryption mappings and history entries expire by their timeout/expire time:
  `src/Netcode.cs:1544-1548`, `src/Server.cs:62`.

**DIVERGENCE: `Server.Stop()` zeroes `_minConnectTokenExpireTimestamp`.**
- Port: `src/Server.cs:422` sets `_minConnectTokenExpireTimestamp = 0` in `Stop()`.
- Behavior: the value is recomputed on every `Start()` at `src/Server.cs:385`,
  so the zero is only visible while the server is not running.
- `STANDARD.md` § Nonce Reuse and Server Restarts explicitly says "The value it
  holds while the server is not running is unspecified, and an implementation
  may leave it at 2^63 or zero it".  This is therefore an allowed choice, but
  the audit candidate noted that the C reference does *not* zero it at
  `C netcode.c:4579-4590`.
- Verdict: `DIVERGENCE` (allowed, standard says unspecified).

**Finding needing C lines: per-mapping challenge sequence for connection responses**
- The C reference is reported to store the challenge-token sequence inside the
  encryption mapping and only accepts a response whose challenge-token sequence
  belongs to that mapping; the C# port does not keep a per-mapping challenge
  sequence.  It decrypts the response with the global server challenge key:
  `src/Server.cs:748-757`.
- Needed: the C reference `netcode_server_process_connection_response_packet` and
  `netcode_encryption_manager_t` challenge-token-sequence field for a file:line.
- Verdict suspended (`QUESTION`) pending those C lines; likely a real BUG
  (replay/validation gap against the reference).

## 4. Server: global sequence seeding, restart floor, challenge/denied, response validation, timeouts, keep-alive rate, disconnect redundancy, max clients, loopback

**Verdict: mostly MATCH; callback ordering needs C lines**

- Global sequence is seeded to `2^63` both in the constructor and on every
  `Start()`: `src/Server.cs:302` and `src/Server.cs:392`.
- Restart-floor ordering in `PacketIO.ReadPacket` checks expiry, then the
  server's `minConnectTokenExpireTimestamp`, then decryption: `src/Netcode.cs:1051-1061`.
- Challenge/denied handling follows `STANDARD.md` § Processing Connection Requests:
  denied when full (`src/Server.cs:707-711`), challenge otherwise
  (`src/Server.cs:729-745`).
- Client timeouts are checked every update: `src/Server.cs:991-1013`.
- Keep-alive send rate is 10 Hz: `src/Netcode.cs:72`, `src/Server.cs:982`.
- Redundant disconnect packets (10) are sent by the server:
  `src/Netcode.cs:73`, `src/Server.cs:569-576`.
- Max clients is 256: `src/Netcode.cs:48`; validated in `Server.Start` at
  `src/Server.cs:368-372`.
- Loopback clients are supported and require the callback:
  `src/Server.cs:1150-1214`.

**Finding needing C lines: loopback disconnect callback timing**
- The port fires `OnClientConnectDisconnect(clientIndex, false)` before clearing
  the client slot in `DisconnectLoopbackClient`: `src/Server.cs:1209-1213`.
- The audit candidate claims the C reference fires the callback *after* clearing
  the slot (`C netcode.c:5472-5477`) and that firing before is a BUG extending
  an earlier fix ("N3").
- This is not specified in `STANDARD.md`.  Verdict suspended (`QUESTION`)
  pending a C checkout to confirm line numbers and observed behavior.

## 5. Client: state machine, sequence, next-server stepping, timeouts, keys/token

**Verdict: MATCH**

- Client states and numeric values match `STANDARD.md` § Client State Machine:
  `src/Client.cs:16-38`.
- Sequence numbers start at zero and are incremented for every encrypted packet
  sent: `src/Client.cs:119`, `src/Client.cs:556-557`.
- Connection request retransmissions step to the next server address when the
  list is exhausted: `src/Client.cs:622-641`.
- Timeouts are driven from `_lastPacketReceiveTime + timeout_seconds < time`
  for connection-request, connection-response and connected states:
  `src/Client.cs:680-712`.
- Token-to-keys assignment uses the token's `ServerToClientKey` for reads and
  `ClientToServerKey` for writes: `src/Client.cs:359-360`.
- Token validity (`create <= expire`, address count, address type) is checked
  when parsed: `src/Netcode.cs:727-728`, `src/Netcode.cs:736-749`.

## 6. Receive loops, callbacks, override-refusal, loopback-refusal, address buffer, simulator allocation, socket errors

**Verdict: multiple findings; C 1.4.6–1.4.8 behavior not fully in `STANDARD.md`**

- Empty datagrams are skipped: the socket receive functions return `0` when
  no packet is available and the loops break; client `src/Client.cs:519-523`,
  server `src/Server.cs:961`.
- The socket drains in `while(true)` until the OS reports no packets; there is
  no per-update cap for real socket receives.  The simulator caps receives to
  `ClientMaxReceivePackets`/`ServerMaxReceivePackets`: `src/Netcode.cs:68-69`,
  `src/Netcode.cs:1448-1469`.  The C reference 1.4.6 may cap every drain;
  pending C lines.
- **MISSING: payload slack.**  The C reference 1.4.6 is reported to carry eight
  bytes of readable slack behind the payload data inside the decrypted packet.
  The C# port treats any decrypted payload size in `[1, MaxPayloadBytes]` as
  valid: `src/Netcode.cs:1210-1221`.  It therefore accepts payloads up to 1200
  bytes and does not expose trailing slack.  This cannot be verified without the
  C checkout; recorded as `QUESTION`.
- **Override callback refusal.**  A config with `OverrideSendAndReceive = true`
  and a missing callback is refused at create time:
  `src/Server.cs:115-117`, `src/Server.cs:251-255`,
  `src/Client.cs:55-57`, `src/Client.cs:160-164`.
  Error codes are 8 (server) and 7 (client), matching the known candidates.
- **Loopback callback refusal.**  Loopback connect is refused when the
  `SendLoopbackPacket` callback is unset: `src/Client.cs:794-798`,
  `src/Server.cs:1155-1159`.
- **Address-string buffer contract.**  Parsing truncates input to
  `MaxAddressStringLength - 1` (255): `src/Netcode.cs:65`,
  `src/Netcode.cs:269-270`.
- **Simulator allocation failure.**  The C# simulator pre-allocates every
  packet-entry buffer once on first use (`??=`) and never drops due to an
  allocation failure: `src/Netcode.cs:1413-1423`.  The audit brief reports the
  C reference (1.4.8) drops the packet and keeps the queued entry on a failed
  allocation, but no C file:line was readable from this job.
  Verdict: `QUESTION`.  Needed to resolve: the C checkout, then the file:line of
  the allocation in `netcode_simulator_send_packet` / the packet-entry insert
  path in `netcode.c` (the branch that returns without enqueueing when the
  allocation fails), so the entry can carry both locations and be graded
  `DIVERGENCE` (allowed: the port does not allocate per packet) or `BUG`
  (the queued entry is lost or the packet is double-counted).
- **BUG: any `SocketException` ends the receive drain.**  `NetcodeSocket.ReceivePacket`
  catches all `SocketException`s and returns `0`, which the caller treats as
  end-of-drain: `src/Netcode.cs:1935-1949`.  In particular `MessageSize`
  errors silently stop the drain instead of being counted as a dropped
  datagram and continuing.  The audit candidate (`C netcode.c:901-923`, line
  quoted from the brief and not verified against a C checkout here) flags
  this as a bug of the N1 family.  This is a real BUG in the port even without
  the C checkout, because a malformed too-large UDP datagram can wedge the
  endpoint until the next update frame.  Port lines: `src/Netcode.cs:1937-1942`.

## 7. Randomness: key/nonce source and behavior on a stubbed RNG

**Verdict: MATCH (with platform caveat)**

- All keys and nonces come from `RandomNumberGenerator.Fill`:
  `src/Netcode.cs:159-166` (`Rng`).  This is used for connect-token keys/nonces
  (`src/Netcode.cs:499-500`, `src/Netcode.cs:823`), the server challenge key
  (`src/Server.cs:383`), and connect-token generation (`src/Netcode.cs:823`).
- On a platform where the OS CSPRNG is unreachable or stubbed, .NET's
  `RandomNumberGenerator.Fill` throws rather than silently using uninitialized
  memory.  This satisfies the intent of `IMPLEMENTERS.md` § 4, but the exact
  failure mode has not been compared line-by-line with the C reference;
  recorded as `MATCH` against the requirement that uninitialised memory must
  not be used.
